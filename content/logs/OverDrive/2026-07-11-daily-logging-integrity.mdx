## 출발점

앱의 메뉴 수보다 중요한 기준은 헬스장에서 세트 사이에, 또는 식사 중에 기록을 얼마나 적은 동작으로 끝내는가였다. 기존 화면은 빠른 입력 경로를 갖고 있었지만, 그 속도가 데이터 정확성까지 보장하지는 않았다.

코드 공격 검토에서 다음 실패가 확인됐다.

- Today, Log, Explore가 독립적으로 세션을 만들 수 있어 동시에 시작하면 open session이 갈라질 수 있었다.
- 세트 행은 이미 저장됐는데 CP·JUICE 같은 파생 작업이 실패하면 UI가 전체 실패로 보고했다. 사용자가 다시 누르면 중복 행이 생길 수 있었다.
- 저장 직후 Edit가 정확한 행을 갱신하지 않고 새 기록 경로로 들어갈 수 있었다.
- Finish와 저장·수정·삭제·Undo가 겹치면 완료 요약과 실제 DB가 달라질 수 있었다.
- 코치는 같은 세션에서 방금 수행한 중량에도 다시 2.5 kg를 더할 수 있었다.
- 확인 카드는 중첩된 터치 영역, 짧은 자동 소멸, 비동기 Undo 중 dismiss 경로 때문에 엄지 한 번의 실수가 복구 동선을 끊을 수 있었다.

## 바꾼 경계

세션 시작은 중앙 coordinator가 조정한다. 명시적 Forge 진입과 silent start가 같은 원자적 시작 경계를 사용하며, implicit 기록 경로에서는 silent 요청을 우선한다.

세션 store에는 mutation과 finish lease를 추가했다. 저장·수정·삭제·Undo와 Finish가 서로 침범하지 못하고, 이중 Finish도 막는다. 앱 재수화와 start/resume도 이미 잡힌 lease를 초기화하지 않는다.

SQLite 행 INSERT를 기록 성공의 기준으로 정했다. CP, Health, streak, JUICE는 파생 작업이며 실패해도 이미 저장된 행을 실패로 되돌리지 않는다. 세트 수정과 삭제는 exact row ID를 exclusive transaction 안에서 처리하고, 이후 DB의 item count와 volume을 다시 읽어 in-memory summary를 맞춘다. 완료는 조건부 `completed_at IS NULL` 갱신이 durable success boundary다.

식사 Undo도 같은 원칙을 쓴다. 한 번 저장된 meal batch의 ID, 원래 날짜, user ID를 보존해 자정을 넘어도 다른 날의 protein discipline을 건드리지 않는다.

## 헬스장 화면 변화

저장 확인 카드는 화면 전체 Pressable 안에 버튼을 중첩하지 않는다. 요약, Edit, Undo가 예측 가능한 형제 터치 영역이고, 15초 동안 유지된다. screen reader가 켜져 있으면 자동으로 사라지지 않으며, Undo 중에는 타이머와 모든 dismiss 경로가 멈춘다. 새 저장이 들어오면 nonce가 달라져 이전 Undo가 새 카드를 지우지 못한다.

Edit는 원본 세트 한 행을 수정하고 새 INSERT, 휴식 타이머 재시작, JUICE 재발화를 하지 않는다. 같은 세션의 코치는 실제 마지막 중량과 횟수를 유지하고, 새 세션의 첫 추천에서만 점진 증량을 적용한다.

스포츠웨어 아바타의 앞·뒤·Cardio 선택은 긴 번역과 큰 글자에서도 wrap되도록 했고, Pill은 고정 높이 대신 최소 높이와 수직 패딩을 사용한다.

## 남은 판정

식사 Repeat→Undo의 실제 터치 완주는 확인하지 못했다. Maestro가 `Repeat last meal` 버튼 36pt 중 17pt만 보이는 상태를 100% visible로 오판했고, ScrollView viewport 밖 1pt를 탭했다. DB 변화와 실패 안내가 모두 없어서 handler 진입 전 자동화 실패로 판정했지만, 다음 실행에서는 버튼을 중앙 정렬한 뒤 음식 행 `1→2→1`과 `Meal removed`까지 확인해야 한다.

실제 헬스장 한 세션과 실제 식사 자리에서 탭 수·오입력·중단 시간이 줄었는지도 아직 미검증이다. 이번 결과는 기능과 시뮬레이터 품질 검증이며, 현장 제품 검증을 대신하지 않는다.
