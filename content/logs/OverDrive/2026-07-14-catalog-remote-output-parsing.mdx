새 production D1에 migration 66 queries와 정본 draft 760 queries를 적용한 뒤 admin verify는 64행, 66,654 bytes, generation 752, 빈 channel을 정확히 읽었다. 첫 `publish --remote`의 D1 file 실행도 실제로는 성공했지만 admin은 `Unexpected token '├'`로 종료했다. Wrangler 4.110이 `--json`에서도 remote file upload progress를 stdout 앞에 쓰고 JSON array를 마지막에 붙였기 때문이다.

mutation 실패 메시지만 보고 즉시 재시도하지 않았다. read-only `verify --remote`를 먼저 실행해 release가 `published`이고 `currentChannelVersion`이 `1.0.0`이며 checksum이 정본과 같은 것을 확인했다. 이 readback으로 write 성공과 client parser 실패를 분리했다.

`parseWranglerJson`은 stdout 전체 JSON을 우선 허용한다. 전체 파싱이 실패할 때만 뒤에서부터 `[` 위치를 후보로 삼고, stdout 끝까지 정확히 소비하는 JSON suffix를 찾는다. 따라서 upload progress prefix는 허용하지만 JSON 뒤 trailing junk는 허용하지 않는다. 반환 배열의 모든 entry가 `success:true`인지 확인하는 기존 fail-closed 조건도 유지했다.

기능 검증은 새 parser의 progress-prefix 성공, trailing-junk 실패, `success:false` 실패 테스트와 전체 Worker 86/86, Node syntax, `git diff --check`를 통과했다. production에 같은 fixed timestamp `1783987201234`를 사용해 publish를 멱등 재시도했고, admin 자체 post-readback을 거쳐 version `1.0.0`, checksum `sha256:43491e64b66fbd16f87325d8e8ea9e5d2325d888b71c700b61b80da19566604a`를 출력하며 종료 코드 0을 반환했다.

구현 커밋은 `7a0d677`이다. 이 수정은 client-side output parsing만 바꾸므로 D1 rollback은 없다. production channel은 이미 같은 immutable release를 가리키고 있으며 Worker code upload와 live HTTP 검증은 다음 단계다.
