## Context & constraints

빌더가 "휴식/음식도 기록하는 종합건강이냐, 운동만 타겟팅이냐"를 물음. 핵심 제약: ① 앱 정체성 = "존나 쉬움 + 기록할 때 개꼴림"(수동 입력 경멸) ② 키 클라이언트 금지(§3) ③ 헬스데이터 컴플라이언스 — 판매/마이닝 금지(§9) ④ Phase 1 = 백엔드 없는 온디바이스.

## Options considered

1. **운동만 타겟팅** — 단순하지만 "종합건강" 차별점 포기.
2. **지금부터 풀 종합건강(수동 음식/수면 로깅)** — 마찰 폭증, 피트니스 앱 최다 이탈 기능(음식 일기), 정체성과 정면 충돌. 기각.
3. **(채택) 종합건강 + 전부 저마찰** — 운동=히어로(지금), 음식=**사진 비전AI**(빌더 제안, Phase 2), 수면/체중=헬스 자동연동(Phase 2/5), Phase 1엔 선택적 원탭 규율(단백질/수면 ✓ → 전투력 규율 컴포넌트).

## Chosen + Why

3안. 빌더 직감("음식은 사진으로 알아서 연동")이 정답 — 수동 음식일기는 마찰 함정. 사진→비전LLM 매크로 추정이 "수동 입력 경멸"과 양립. 스펙도 이미 이 방향(전투력에 규율 컴포넌트, §6.7 ML Kit, §7 서버 LLM, BodyComp Phase 5). 종합건강을 "음식일기"가 아니라 "사진AI + 헬스 임포트"로 달성.

## Trade-off accepted

- 음식 기능이 Phase 2까지 미뤄짐(서버 필요). Phase 1은 운동+규율 토글에 한정.
- 사진 칼로리는 추정(정밀 매크로 아님) → "규율/트렌드 신호"로 포지셔닝.

## Reversibility / Verified by

- 가역적: 범위 문서일 뿐, 코드 잠금 없음. Phase 2 착수 전 재검토 가능.
- Verified by: 이 대화의 빌더 결정("음식은 사진으로") + 스펙 §3/§6.7/§7/§9 정합.

## 다음

- Phase 1: (선택) 단백질/수면 원탭 규율 토글 → 전투력 규율 컴포넌트 활성. 운동 뽕맛 계속.
- Phase 2: 사진 음식 로깅(서버 비전LLM, 키 서버사이드) + Apple Health/Health Connect 임포트(수면/체중/심박).
