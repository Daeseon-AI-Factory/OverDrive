## 출발점

사용자 피드백은 두 가지였다. 헬스장과 식사 중 기록은 한두 번의 동작으로 끝나야 하고, 기존 4탭과 정적 부위 목록은 실제 운동을 찾는 데 도움이 되지 않았다.

코드에서도 같은 문제가 확인됐다. 탭은 `Today / Power / History / Settings` 네 개였고, 부위 picker는 `REGIONS[region].exerciseIds`만 조회했다. QuickLog가 DB에 만든 ad-hoc 운동은 최근 기록 칩 외에는 다시 찾을 경로가 없었다. 첫 시뮬레이터 점검에서는 유산소가 `Bodyweight · 0–0 reps`로 표시됐다.

## 바꾼 구조

- 탭을 `Today / Explore / Log / History / Settings`로 재편했다. 전투력은 사라진 기능이 아니라 Today의 CP 헤더에서 여는 상세 화면으로 이동했다.
- 중앙 Log는 근력 QuickLog, 전체 근력/유산소 picker, FoodCard를 한 화면에 모았다. 음성 입력은 근력 전용임을 명시해 음식까지 지원하는 것처럼 보이지 않게 했다.
- Today는 상황에 따라 순서를 바꾼다. 진행 중이면 세션·최근 세트 기록이 먼저이고, idle이면 지난 식사 반복이 코치 다음에 온다.
- Explore는 전체 검색, 근력/유산소 카탈로그, 6개 부위 칩, 기존 그래픽 바디맵을 함께 제공한다.
- 검색은 현지화 이름, DB 이름, slug 토큰, 근육군, 현지화 부위어를 대상으로 한다. 빈 검색은 부위별 curated 목록을 유지하되 최근 사용 운동을 앞으로 보낸다.
- FoodCard는 마지막 식사를 한 번에 반복한다. 한 식사의 여러 행은 단일 다중행 `INSERT`로 저장돼 SQLite statement-level 원자성을 가진다.

## 출고 전 잡힌 실패 모드

독립 리뷰에서 두 데이터 무결성 문제를 발견했다.

1. 검색 결과를 선택하는 순간 세션을 만들면, 로거를 닫기만 해도 0세트 open session이 남는다. Boot가 이를 복원하고, 사용자가 완료하면 실제 운동 없이 세션·streak·CP에 들어갈 수 있었다. 세션 생성은 Set/Cardio logger의 실제 저장 시점으로 미뤘다.
2. `withTransactionAsync`는 expo-sqlite 공유 연결에서 비독점이다. 다른 세트/CP 쓰기가 식사 트랜잭션에 섞일 수 있어, 식사 실패가 무관한 기록을 함께 롤백할 위험이 있었다. 한 번의 다중행 `INSERT`로 교체했다.

picker와 logger의 두 Modal도 한 프레임 지연으로 이어 붙이지 않았다. iOS native slide 종료를 `Modal.onDismiss`에서 받은 뒤 logger를 열도록 바꿨다.

## 검증

- `npm test -- --runInBand`: 25 suites, 197 tests 통과.
- `npm run typecheck`: strict TypeScript 통과.
- `npm run lint`: 경고/오류 없이 통과.
- `npx expo run:ios --configuration Release --device "iPhone 17 Pro"`: 빌드 성공, 0 errors / 기존 경고 3건.
- DB seed + 실제 UI 조작: 중앙 Log, 근력/유산소 picker, 영문 `bench`, 한글 `스쿼트`, picker→logger 전환, CP 상세→뒤로가기를 확인했다.
- 선택 후 저장 없이 닫기: `workout_session` 총 5건 / open 0건이 전후 동일했다.
- 지난 식사 반복 1회: 2행·640kcal·69g에서 4행·1280kcal·138g, distinct meal batch 2개로 저장됐다.
- 앱 완전 종료·재실행 뒤 진행 중 세션이 `IN SESSION · Set 2/3`으로 복원됐다.
- 검증 후 시뮬레이터 DB·WAL·SHM은 사전 백업과 SHA-256이 일치하도록 복원했다.
