## 왜 순서를 바꿔 이걸 먼저

빌더 결정이 **"코드부터, 빌드는 나중에"** 였다. 화면/셰이더/네이티브(Skia·sqlite)는 dev client 빌드가 있어야 실행을 볼 수 있지만, **전투력 산식은 순수 함수라 jest로 지금 당장 검증**된다. 게다가 스펙 §10이 전투력 계산을 단위테스트 의무 대상으로 못박았다. 그래서 플랜의 빌드 순서(테마→DB→JUICE→전투력) 대신 **검증 가능한 순수 코어(전투력)를 선행**했다.

## 산식 (플랜 §3 그대로)

```
basket01  = Σ_i ( w_i_eff · s_i )            // 활성 컴포넌트만 가중평균, ∈[0,1]
trustMult = 1 + 0.15·clamp01(verifiedRatio)  // 항상 >= 1 (자기보고 무처벌)
score     = clamp( round(9999 · basket01 · trustMult), 50, maxScore )
```

- 컴포넌트: 근력볼륨 `sat(v,15000)` · 세션 `ramp(n,5)` · 컨디셔닝 `sat(u,90)` · 연속 `sat(d,10)` · 규율 `(단백질/7+휴식/7)/2`. 리컴프·체력마커는 Phase 5라 **비활성**.
- `sat(x,k)=1-e^(-x/k)` — 천장 없는 포화(추격감). `ramp`는 cap까지 선형.
- 등급(오리지널): 일반인 0 / 루키 800 / 파이터 2000 / 워리어 3500 / 비스트 5000 / 괴수 6500 / 초월자 8200.

## 설계 결정 3가지

1. **graceful renorm.** 비활성 컴포넌트는 분모에서 빼고 활성 가중치를 1로 재정규화. → 미래(리컴프/마커) 데이터가 없다고 점수에 **숨은 천장**이 생기지 않는다. (테스트 #5: discipline null + 4컴포넌트만으로도 9999 도달 가능.)
2. **anti-shame.** 빈 주 = floor 50(0 아님). `trustMult`는 절대 1 미만 X — 검증 데이터는 **보너스(+0~15%)** 일 뿐 자기보고를 깎지 않는다. 약한 하루도 빈 주보다 점수 높음.
3. **breadth-gate (튜닝 다이얼).** 최상위 초월자(8200+)는 **검증/마커 breadth** 필요 → Phase 1 자기보고만으론 괴수(8199) 캡. 플랜이 "자기보고만으로 초월자 허용?"을 빌더 콜로 남겼기에, 기본 ON으로 구현하되 상수로 끌 수 있게 했다.
